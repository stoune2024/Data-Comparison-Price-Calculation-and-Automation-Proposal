# Data Comparison, Price Calculation and Automation Proposal

## Описание

Проект представляет собой сервис на **Python + FastAPI**, который выполняет обработку Excel-файла согласно тестовому заданию:

* сопоставляет товары из выгрузки 1С с товарами маркетплейса;
* рассчитывает минимальную цену продажи при рентабельности вложенных средств не менее **30%**;
* формирует итоговый Excel-файл с результатами обработки.

---

* Python 3.12
* FastAPI
* Pandas
* OpenPyXL
* RapidFuzz

Установка зависимостей

```bash
pip install -r requirements.txt
```

Запуск приложения

```bash
uvicorn app.main:app --reload
```

Swagger будет доступен по адресу

```
http://localhost:8000/docs
```

Основной endpoint

```
POST /process
```

Принимает Excel-файл и возвращает обработанный результат.

### Domain

Содержит исключительно бизнес-модели и абстракции.

* модели предметной области;
* перечисления статусов;
* интерфейсы сопоставления товаров;
* интерфейсы расчета цены.

Слой не зависит от FastAPI, Pandas и других внешних библиотек.

---

### Infrastructure

Отвечает за работу с внешним миром.

В проекте реализованы:

* чтение Excel;
* запись Excel;
* алгоритм поиска совпадений товаров;
* вспомогательные функции нормализации.

---

### Services

Содержит бизнес-логику.

`ProcessingService` координирует процесс обработки:

```
Excel
    ↓
чтение
    ↓
сопоставление
    ↓
расчет цены
    ↓
запись результата
```

`PricingService` отвечает исключительно за расчет минимальной цены.

---

### API

FastAPI используется только как транспортный слой.

Endpoint получает файл, передает управление сервису обработки и возвращает готовый Excel.

Бизнес-логика при этом полностью изолирована от HTTP.

# Принятые архитектурные решения

При реализации проекта основной целью было соблюдение баланса между качеством архитектуры и объемом решения.

Проект небольшой, поэтому сознательно не использовались дополнительные уровни абстракции, не приносящие практической пользы.

При этом были соблюдены базовые инженерные принципы.

## Single Responsibility Principle

Каждый класс отвечает только за одну задачу.

* ExcelReader — чтение файла.
* ExcelWriter — запись результата.
* FuzzyMatcher — сопоставление товаров.
* PricingService — расчет цены.
* ProcessingService — координация процесса обработки.

---

## Dependency Inversion Principle

`ProcessingService` зависит от интерфейсов (`ProductMatcher`, `PricingCalculator`), а не от конкретных реализаций.

Это позволяет заменить алгоритм сопоставления или расчета без изменения основного сервиса.

---

## Dependency Injection

Все зависимости создаются централизованно через `dependencies.py`.

Сервисы не создают свои зависимости самостоятельно, что упрощает тестирование и замену реализаций.

---

## KISS

Основной акцент сделан на простоте.

В проект не добавлялись Repository, Unit of Work, Factory, Strategy и другие паттерны, поскольку отсутствует база данных, несколько источников хранения или различные сценарии расчета, где подобные абстракции были бы оправданы.

---

## DRY

Повторяющаяся логика вынесена в отдельные сервисы и вспомогательные функции.

Например:

* нормализация строк;
* преобразование значений в числовой формат;
* расчет цены;
* сопоставление товаров.

---

# Алгоритм сопоставления

Поиск выполняется в два этапа.

1. Нормализация артикулов и поиск точного совпадения.
2. Если совпадение отсутствует — поиск по названию товара с использованием RapidFuzz (`token_sort_ratio`).

В зависимости от степени совпадения присваивается один из статусов:

* сопоставлено;
* требуется ручная проверка;
* не найдено;
* отсутствует себестоимость.

Приоритет отдавался минимизации ложных совпадений, поскольку согласно условию задания ошибочное сопоставление считается более серьезной ошибкой, чем отсутствие найденного соответствия.

---

# Расчет цены

Минимальная цена рассчитывается исходя из условия

```
Рентабельность = Прибыль / Себестоимость
```

с учетом:

* себестоимости;
* комиссии маркетплейса;
* обработки нестандартного товара;
* логистики;
* доставки до места выдачи.

Полученное значение округляется вверх до целого рубля, что гарантирует сохранение требуемой рентабельности.

# Ответ на задание №3

При выполнении тестового задания использовались следующие инструменты.

### Python

Основной язык реализации сервиса.

Использовался для реализации бизнес-логики, сопоставления товаров и расчета минимальной цены.

---

### FastAPI

Использовался для создания HTTP API.

Позволяет загрузить Excel-файл и получить готовый результат без написания дополнительных пользовательских интерфейсов.

---

### Pandas

Использовался для чтения и формирования Excel-файлов.

После чтения данные преобразуются в доменные модели, благодаря чему бизнес-логика не зависит от DataFrame.

---

### OpenPyXL

Используется Pandas для работы с файлами Excel формата XLSX.

---

### RapidFuzz

Использовался для нечеткого поиска совпадений по названию товара.

Позволяет учитывать различия в порядке слов, небольшие опечатки и особенности написания.

---

### Принципы проектирования

При разработке использовались принципы ООП и SOLID.

Дополнительно применялся Dependency Injection для управления зависимостями между компонентами.

Основной целью было сохранить архитектуру простой и расширяемой без преждевременного усложнения.

# Ответ на задание №4

При обработке десятков тысяч SKU и регулярном получении выгрузок процесс целесообразно автоматизировать полностью.

Возможный вариант развития решения:

* получать данные как из Excel, так и через API маркетплейсов;
* добавить поддержку различных форматов входных файлов;
* автоматически определять структуру выгрузки по заголовкам колонок;
* сохранять подтвержденные сопоставления товаров в базе данных;
* повторно использовать ранее найденные соответствия;
* выполнять обработку по расписанию;
* вести журнал обработки и статистику качества сопоставления;
* реализовать уведомления об ошибках обработки;
* при необходимости распараллелить обработку больших файлов.

Подобная архитектура позволит без существенных изменений масштабировать решение на десятки и сотни тысяч товаров.

Несмотря на то, что текущая реализация полностью соответствует требованиям тестового задания, в реальном проекте можно рассмотреть следующие доработки.

* Кэширование результатов сопоставления.
* Хранение подтвержденных сопоставлений в базе данных.
* Поддержка нескольких маркетплейсов через отдельные реализации `ProductMatcher`.
* Добавление полноценного логирования.
* Покрытие проекта unit- и интеграционными тестами.
* Настройка CI/CD.
* Контейнеризация приложения с использованием Docker.
* Добавление валидации входных файлов и более подробной обработки ошибок.

При этом большинство перечисленных улучшений не были реализованы намеренно, поскольку для текущего объема проекта они привели бы к усложнению архитектуры без существенной практической пользы. Основной целью являлось соблюдение требований задания, сохранение читаемости кода и возможность дальнейшего расширения проекта без необходимости его переработки.
